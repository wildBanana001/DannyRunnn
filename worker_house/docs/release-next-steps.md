# 接下来怎么做：接口化改造发布清单

本清单针对活动、商品、订单改为服务端真源后的首次切换。代码已准备不等于线上已验证；推送 `main` 按现有部署配置会触发云托管发布。

2026-09-06 已确认的方向：准备正式售卖，但先用 ¥0.01 单价完成一轮端到端验收；验收通过后，正式价格由负责人另行确认。本轮不擅自调整库存、运费、上下架或活动档期，单价一分钱也不等于多件/含运费订单的总额必为一分钱。

这轮测试按 [一分钱验收清单](one-cent-acceptance.md) 逐项执行和留证；测试结果不能用本地构建成功替代。

## 1. 先完成代码门禁（可由开发代理执行）

- BFF：`npm test`、`npm run test:mysql`、HTTP smoke、生产 Docker 构建。
- 小程序：`npm test`、类型检查、生产 `cloudrun` 构建、`npm run verify:production-bundle`。
- `BFF CI` 已配置 MySQL 8 独立 `worker_house_test` 库。专用 `test:mysql` 命令缺连接地址、测试跳过或失败时必须失败；普通本地 `npm test` 没有测试库时仍会跳过目录、订单并发与调价三个数据库用例。
- 集成测试会清理测试数据和目录种子状态，只能连接可销毁的专用测试库，不能使用生产库或共享验收库。
- 先提交独立 PR，确认 BFF 和小程序 CI 都通过，再批准合并。Git Webhook 与 CI 是独立触发链路；仅存在 CI 文件不能保证“CI 通过才部署”，还需在仓库配置合并保护，或使用人工发布审批。
- 提交前单独检查现有 `worker_house_bff/dist` 与 `node_modules` 的大量工作区变更，不能把它们随业务改动一并暂存。

## 2. 核对首次迁移的数据（需要运营事实，不猜测）

先备份目标数据库和旧实例的活动/商品权威目录。旧实例文件中运营修改过的内容不会自动进入新 MySQL。

当前仓库种子仅作为核对起点，**不是线上现状证明**：7 款启用商品都是 ¥0.01 且 `stock=null`；3 个启用活动已按本轮验收要求统一为 ¥0.01（手作活动此前单价为 ¥148，`originalPrice` 展示值保持不变）。日期都在 2026 年 8 月，以本清单编写日期 2026-09-06 看，这些活动均已结束；测试报名需明确指定新的测试档期，不能直接重新开放过期活动。

需要负责人确认：

- 验收通过后，每项商品/活动的正式价格；同时核对运费、限购和履约方式。原价备份用于撤销本轮测试调价，不自动代表最终正式定价。
- 商品是不限库存还是有限库存，下一批活动的日期、名额与上架状态。
- 旧系统的活动基础人数是否已包含历史已付报名，避免导入后重复计数。

库存语义：`stock` 是历史 `paid` 加当前 `pending` 数量的总上限，不是“此刻剩余库存”；`null` 明确表示不限。活动接口显示人数是基础 `currentParticipants` 加已付报名订单数。

首次种子风险：`worker_house_catalog_state.seed_version < 1` 时，初始化会 UPSERT 种子，同 ID 的预填数据库记录会被覆盖。若导入真实运营目录，应在受控事务里完成目录和种子状态的同步，审核导入方案后再启动新版。不要只预填业务表，也不要为了刷新配置而清空种子状态。初始化完成后，修改仓库 JSON 并重新部署不会更新生产目录。

## 3. 数据库与发布顺序（批准后执行）

1. 确认环境、版本、备份和发布窗口；暂停新单，等待在途创建请求结束，保留支付回调和历史订单查询。若涉及旧存储订单迁移，另行设计对账窗口，不能直接关闭回调了事。
2. 001/002/003 已包含在容器建表清单、自动迁移及 `npm run migrate:orders` 中。`MYSQL_AUTO_MIGRATE=true` 会幂等建表，不必重复手工执行同一组 SQL。若使用人工迁移，应先运行迁移再关闭自动迁移，并确保运行账户权限符合后续读写需求。
3. 核对 MySQL 中订单表、活动表、商品表、目录状态表、活动锁和商品库存锁，以及以下标记。建表成功不代表真实目录已迁移。

   ```sql
   SELECT version, applied_at FROM worker_house_schema_migrations ORDER BY version;
   SELECT catalog_name, seed_version, seeded_at FROM worker_house_catalog_state ORDER BY catalog_name;
   SELECT COUNT(*) AS activity_count FROM worker_house_activities;
   SELECT COUNT(*) AS product_count FROM worker_house_shop_products;
   ```

   预期含 `001_mysql_order_storage`、`002_mysql_catalog_storage`、`003_mysql_shop_stock_reservations`；目录状态含 `activities`、`products` 且版本至少为 1。还须逐项核对 ID、金额、上下架、库存与人数，而不只核对条数。
4. 新版切到 100% 流量且目录核对通过后，执行无交易验收，再决定是否开启新单。避免新旧实例分别读文件与 MySQL 时混合售卖。

## 4. 运行无交易验收

在 `worker_house_bff` 目录使用 Node.js 20+，确认 HTTP 访问地址后执行：

```bash
BFF_BASE_URL=https://已确认的服务域名 npm run check:release -- --expect-shop=closed
```

开单获批并启用后，再使用 `--expect-shop=open`。脚本默认要求商城关闭，不会帮你打开开关；任一必要检查失败会退出非零。

脚本检查存活、CloudRun/MySQL 数据源、商城开关、支付/履约配置、站点能力、公开活动和商品列表；检测到 ¥0.01 或不限库存会提示人工核对。空目录也会提示，不擅自创建活动或商品。

边界必须知道：

- 脚本仅调用 6 个公开 GET，不创建订单、不发起支付、不改配置、不输出业务响应明细或密钥。但服务端 readiness 在首次检查且自动迁移开启时可能建表，所以不是“绝对无数据库写入”。
- 当前生产关闭遗留文件能力时，`/api/health` 返回 503 是预期；脚本按实际字段判断，不把这个状态当成容器故障。
- readiness 是配置与存储初始化检查，存储结果会缓存；不等价于微信支付连通成功，也不是持续数据库探活。
- 列表检查不是全量目录对账，活动只取前 100 条；图片、详情、上下架、历史订单还需体验版验收。
- 若云托管只允许 `wx.cloud.callContainer`，用微信开发者工具通过相同接口验收；不要为了脚本关闭网关鉴权或公开管理接口。

另行验收：经管理员授权的签名连通校验、指定体验账号的一笔支付/取消/重试、历史订单和履约核销。真实支付会产生账务，必须先确认验收订单、金额和后续处理方式。密钥只放 Secret/本地受控环境，不贴到聊天或 Git。

## 5. 回滚约束

这次从容器文件目录切换为 MySQL，旧版不具备同等目录和有限库存保护，不能直接恢复流量后继续售卖。

发生问题先关闭新单并保留回调/查单；核对两版目录差异、新产生订单和库存后选择兼容版本。002/003 是新增表，回滚代码不应删除表、清空种子状态或恢复旧订单备份覆盖新订单。事先记录可用回滚版本、负责人和对账方式。

## 6. 发布稳定之后再补的能力

优先补商品管理接口和管理入口（鉴权、配置校验、上下架、操作审计）；接着将首页站点配置迁入持久化存储。用户资料与地址迁移排在配送能力正式开放之前。次卡保持关闭，等购买、支付与权益扣减形成完整链路再开放。

这些代码、测试和文档可以继续由开发代理完成；正式价格/档期、历史数据取舍、生产发布和真实支付验收需要负责人确认。当前清单本身不授权线上修改。
